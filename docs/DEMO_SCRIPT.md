# Selection-round demo (60 seconds)

Use the real app with configured keys and one synthetic resolved incident already retained. Open source details before recording so the audience can see provenance. Label all synthetic inputs clearly.

**0–10s — Business problem**
“On-call engineers lose time repeating investigations their team has already done. Recall keeps the outcome and failed attempts, then uses them in the next incident.”

**10–28s — Memory makes a visible difference**
Open Memory comparison, select Recurring Redis timeout, submit. Both sides receive the same incident and instructions. Point to the historical pool change and its cited Hindsight fragment. Say what the actual output shows; do not claim every run will prefer a particular fix.

**28–43s — Memory must not become blind repetition**
Open the saved synthetic ‘Redis timeouts despite spare capacity’ investigation. Show that the pool is only 28% used, while packet loss is 12%. The live test favored investigating the recent network change despite recalling the old pool fix.

**43–55s — Close the learning loop**
Show Add what happened next and the outcome form. Explain that failed attempts are retained too, and only confirmed recovery is marked resolved. Demonstrate a pre-recorded update if live provider latency would exceed the slot; label it honestly.

**55–60s — Value**
“The next engineer starts with the team's experience, the source behind the advice, and a check that can prove the old fix wrong.”

## Before presenting

- Check connections and rehearse the real requests once.
- Keep one saved live result available if network access fails; identify it as a previous live run.
- Never show API keys, real customer logs, or credentials in the recording.
- Do not claim reduced downtime or measured accuracy without a separate evaluation.
- Record the required content and complete the organizer's profile/submission forms separately. Nothing has been submitted automatically.
